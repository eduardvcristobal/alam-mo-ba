### Roles
- `SUPER_ADMIN`: all platform operations (cannot review their own authored fact).
- `CONTENT_ADMIN`: draft content management and publication after independent review.
- `EDITOR`: author drafts and submit for review.
- `REVIEWER`: independently verify cited sources, approve/reject requests.
- `SUPPORT`: dashboard/read-only content visibility (no authoring, approval or publication).

All API routes under `/api/v1/admin` require a valid **account** session plus an admin role. A guest capability never grants admin privileges. Public registration does not grant an admin role.

### Publishing safeguards
- A draft needs both `en` and `fil` text and appropriate Student/Explore audience before approval.
- Facts need an HTTPS source title and URL. An independent reviewer must explicitly verify the source; source inspection is a human responsibility.
- Authors cannot approve their own drafts, even if also a reviewer.
- Only `APPROVED` items may be published, and quiz questions also require a published and verified linked fact.
- Public learner API excludes draft/unapproved facts and correct answer flags.
- Edits reset unpublished content to Draft; published content cannot be hard deleted, only retired. All transitions are audited.

### Trusted administrator provisioning
No default admin and **no public role-grant API** are created. To initialize a platform owner, an authorized database administrator must:

1. Establish an **existing active account** with a verified Google `sub` identity using a controlled, authenticated method. Do not use display name or email alone as proof of identity.
2. Independently confirm the intended account UUID from the `learning_account_identity` table. Never accept an arbitrary UUID claimed by a browser.
3. In a privileged PostgreSQL session, grant the narrowly required role, for example:

```sql
-- Replace with a VERIFIED existing account UUID. Privileged operator only.
INSERT INTO platform_admin_role(account_id,role)
VALUES ('00000000-0000-0000-0000-000000000000','SUPER_ADMIN');
```

4. Set `GOOGLE_CLIENT_ID` and `ADMIN_GOOGLE_LOGIN_ENABLED=true` only for the approved environment. For the frontend, set `VITE_ADMIN_GOOGLE_CLIENT_ID` to the same Google web client ID, `VITE_ADMIN_LOGIN_ENABLED=true`, and configure the exact permitted JavaScript origins in Google Cloud.
5. Validate `/admin` access, issuer/audience/nonce enforcement and logout in a secured environment. Leave public account registration disabled.

The dummy UUID in this example **must never be executed as-is**. Admin role grants and bootstrap changes require an operational change record and independent authorization.
