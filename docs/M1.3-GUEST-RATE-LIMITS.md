# M1.3 — Guest API Rate Limits

## Defaults

The API applies process-local fixed-window limits using `HttpServletRequest.getRemoteAddr()`:

| Operation | Default per client address |
|---|---:|
| `POST /api/v1/guest/sessions` | 5 per 60 seconds |
| `PUT /api/v1/guest/progress` | 60 per 60 seconds |

Over-limit responses use HTTP 429, a `Retry-After` header, a small JSON error body and `Cache-Control: no-store`. Guest reads and revocation are not rate limited by this change. Limits count requests before controller authentication/validation.

## Configuration

Set these environment variables on the API:

- `APP_RATE_LIMIT_GUEST_WINDOW_SECONDS` (default `60`)
- `APP_RATE_LIMIT_GUEST_SESSION_CREATIONS_PER_WINDOW` (default `5`)
- `APP_RATE_LIMIT_GUEST_PROGRESS_WRITES_PER_WINDOW` (default `60`)
- `APP_RATE_LIMIT_GUEST_MAX_TRACKED_KEYS` (default `10000`)

The key table is bounded. When at capacity, new client keys are rejected until expired entries are cleaned; existing keys continue to work. Set positive values only.

## Deployment limits

- Counters live in one API process; multiple replicas do not share counters. Apply equivalent or stricter limits at the ingress/WAF for multi-instance deployments.
- Forwarded-IP headers are not trusted by this code. Configure the servlet container with a known trusted proxy chain before relying on client IPs behind a reverse proxy, and retain edge rate limiting.
- IP-based limits can group learners behind the same NAT. Review thresholds against real usage before public deployment. This is a development safeguard, not a complete abuse-control or production certification.

## Acceptance

- Unit tests cover thresholds, window reset, key isolation, bounded-key behavior, 429/Retry-After, and ignored spoofed forwarding headers.
- PostgreSQL smoke runs lower test thresholds and confirms live 429 responses for session creation and progress writes.
